Our scope
Purpose limitation Art. 5 §1(b) GDPR

“Personal data shall be collected for specified, explicit and legitimate purposes and not further processed in a manner that is incompatible with those purposes.”

User consent Art. 6 §1(a) GDPR

“Processing shall be lawful only if the data subject has given consent to the processing of his or her personal data for one or more specific purposes.”

There is little guidance on how to enforce these data protection requirements.
Traditional approach: developers enforce these principles directly in code.

Privacy model
( PDpersonal data, Π, ⊑Πpurposes and their hierarchy, DPdeclared purpose policy, apactual purpose mapping )
We define personal data at the level of class properties (its attributes and association ends).
Let Π be a set of purposes.
They form a lattice ordered by set inclusion: ⊑Π  =  ( 2Π,  ⊆ )
Declared purposes describe what the application is allowed to use personal data for.
Each policy rule specifies a purpose, a personal data access, and an additional condition. Example: “We use your name for the FUNCTIONAL purpose, if you are a regular user.”
Actual purposes capture what the data is actually used for during execution.
We associate actual purposes with the application entrypoints and class methods. Example: We associate the Event view_event() method with Functional purpose.

2 Actual purpose tracking
At run time we maintain a stack of actual purposes.
  • When a function f is invoked, its actual purpose ap(f) is pushed onto the stack.
  • When a function returns, its actual purpose is popped off the stack.
ap(foo) = Pa,   ap(bar) = Pb
foo():
...
bar()
...
call stack
bar() → Pb
foo() → Pa
actual purposes = [ Pa, Pb ]
3 Purpose limitation & consent checking
When an action on personal data is invoked, we check two things:
  • Purpose limitation: every purpose in the actual purpose stack must be declared.
  • Consent checking: the owner of the accessed data must have consented to it being used for the actual purpose.
If either check does not hold, the data is restricted from being shown, or the action is suppressed.

  • Policy adequacy: normalize and compare submissions with solutions
  • Coding effort (LoC): line diff of submission against the base implementation
  • Time effort: responses from the survey
Privacy tests

Each test checks whether a user may perform an action on a piece of personal data at a specific endpoint. Three modes of the owner’s consent:

  • <no-consent>: the owner consented to nothing, so every use of their personal data must be denied.
  • <basic>: the owner consented to a basic purpose, so consent checking permits access at a related endpoint.
  • <complex>: the owner consented to a complex purpose, so consent checking permits access at a related endpoint.
Results

Better privacy compliance

Average percentage of failed tests: total number of failed tests ÷ total number of tests

Development: νActionGUI produces ~ 3.5× fewer failed privacy tests than Flask.

Evolution: νActionGUI number is also lower.

Results

…and less effort

Development effort: lines of code changed ÷ number of passing tests

Time effort: self-reported hours

νActionGUI needs about 5× fewer lines of code per passing test, in all phases.

It also takes less time, but the difference is not significant.

Modeling privacy is worth it!

We propose a model-driven methodology for data protection requirements, i.e., purpose limitation and user consent, in software systems.

  • Requirements are defined through formal models.
  • Predefined model transformations generate the enforcement mechanisms automatically.
  • We conducted a two-year empirical study to compare against code-centric development.
  • Result: less effort, better maintainability, and substantially fewer privacy violations.
